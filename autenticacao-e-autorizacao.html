    8. Autenticação e autorização

    Duas perguntas distintas se colocam a cada requisição:

    • Quem é o usuário? Isso é autenticação: o usuário se identificou com um nome de usuário e uma senha, e cada requisição seguinte deve provar que vem dele;
    • Ele tem permissão para acessar esta página? Isso é autorização: no estudo de caso, somente um usuário com o papel ADMIN gerencia médicos e clientes.

    A prova de identidade deve acompanhar cada requisição. O [Django] tem uma aplicação de autenticação completa, [django.contrib.auth]: um modelo [User] (uma tabela do banco de dados), um middleware que guarda o usuário logado em [request.user], views de login e logout, permissões, grupos e a interface de administração que os gerencia. Ela guarda o usuário logado em sua sessão (veja o capítulo sobre escopos), que é a solução mais simples para uma aplicação web. O estudo de caso, em todas as suas versões ([ASP.NET Core MVC], [Spring MVC], [NestJS], [Flask], [Laravel], [Symfony]), usa em vez disso um token JWT (JSON Web Token), que usaremos aqui: após o login, o servidor gera um token contendo a identidade do usuário e o assina com uma chave secreta (é o princípio do cookie assinado do Exemplo 23). O token é guardado em um cookie; o navegador o reenvia a cada requisição; o servidor verifica a assinatura. O usuário pode ler seu token, mas não pode modificá-lo: qualquer modificação invalida a assinatura. O formato é padronizado (RFC 7519), compreendido por todas as linguagens de programação, e o token inclui sua data de expiração. Mais importante, o servidor não precisa guardar nada: qualquer servidor que conheça a chave pode verificar o token.

    Os usuários do estudo de caso são os de sua própria tabela, [users], e não os de [django.contrib.auth]; os próprios tokens não têm lugar em [django.contrib.auth]. Implementaremos, portanto, a autenticação por conta própria, com as ferramentas que já conhecemos, o que tem a vantagem de deixar tudo transparente:

    • um middleware (Exemplo 03) determina, a cada requisição, quem é o usuário com base no token de seu cookie e o inclui na requisição ([request.user], Exemplo 12). O restante da aplicação vê apenas esse resultado;
    • decoradores (exemplo 08) protegem as views: [@login_required], [@role_required("ADMIN")];
    • as senhas são verificadas com as funções de hash do [Django] ([django.contrib.auth.hashers], que podem ser usadas sem o restante da aplicação [auth]);
    • as negações de acesso são exceções [PermissionDenied], convertidas em uma página de erro por uma view [handler403] (Exemplo 24);
    • as tentativas de login são limitadas usando o cache do [Django] (Exemplo 27).

    A criação e a verificação dos tokens ficam a cargo da biblioteca [PyJWT], a mais usada em [Python], instalada pelo arquivo de exemplo [requirements.txt] (ela é importada com o nome [jwt]). (Existem bibliotecas de token JWT para o [Django], como [djangorestframework-simplejwt], concebidas para APIs; para uma aplicação web, bastam algumas linhas, que ilustram melhor o mecanismo.)

from dataclasses import dataclass, field


@dataclass(frozen=True)
class User:
    login: str
    name: str
    # o papel: USER ou ADMIN
    role: str
    # o HASH da senha (vazio para um usuário lido de um token)
    password_hash: str = ""
    # o conteúdo do token que autenticou o usuário; field(default_factory=dict):
    # um dicionário vazio NOVO para cada objeto
    claims: dict = field(default_factory=dict)


# NUNCA guardamos uma senha, apenas seu hash, calculado uma vez por todas
# pela função make_password do Django (algoritmo PBKDF2-SHA256, 1.500.000
# iterações, um salt aleatório):
# python -c "from django.conf import settings; settings.configure();
#            from django.contrib.auth.hashers import make_password; print(make_password('marie'))"
USERS = {
    "marie": ("Marie Pélissier", "USER",
              "pbkdf2_sha256$1500000$pjnFn2tL1G4bu5rVFTv6sZ$Y6v+fj3dC+Y0LZYJGxeE1OOi9beaZVuMVm6R6tljEwI="),
    "admin": ("Administrator", "ADMIN",
              "pbkdf2_sha256$1500000$UTT2hXVaLIEAuGHPFxgnv9$D9+Owt9lDG14VrvArR3n0GGQXWjY9Sg8cgFwip4+yx4="),
}


def find(login: str) -> User | None:
    if login not in USERS:
        return None
    # o "desempacotamento" de uma tupla: seus três elementos em três variáveis
    name, role, password_hash = USERS[login]
    return User(login, name, role, password_hash)

Os dois últimos atributos têm um valor padrão. Para um dicionário, esse valor não pode ser escrito como [claims: dict = {}]: esse dicionário seria criado uma única vez e compartilhado por todos os objetos. [field(default_factory=dict)] instrui [@dataclass] a chamar [dict()] para cada novo objeto;
    • linhas 20–24: um servidor nunca guarda uma senha, nem mesmo criptografada: se o banco de dados fosse roubado, as senhas seriam roubadas junto (e muitas pessoas usam a mesma senha em todo lugar). Ele guarda o resultado de uma função de hash, uma função unidirecional: é possível calcular o hash de uma senha, mas não é possível recuperar uma senha a partir de seu hash. Para verificar uma senha digitada, calcula-se seu hash e compara-se com o que está guardado no banco de dados;
    • linhas 25–30: dois usuários de teste, fixados no programa (o Exemplo 28 e o estudo de caso os colocarão em um banco de dados): para cada login, o nome, o papel e o hash da senha. O hash foi calculado de uma vez por todas pela função [make_password] do [Django] (o comando é fornecido em um comentário), com seu algoritmo padrão, PBKDF2-SHA256. O hash guardado tem quatro partes, separadas por [$]: o algoritmo ([pbkdf2_sha256]), o número de iterações, o salt e, por fim, o resultado. Um bom algoritmo de hash de senhas tem duas características. É intencionalmente lento, com um nível de lentidão ajustável: o PBKDF2 aplica a função SHA-256 1.500.000 vezes, o que leva algumas centenas de milissegundos — imperceptível para um usuário, mas que torna muito custoso para um invasor tentar bilhões de senhas; o [Django] aumenta esse número a cada versão para acompanhar o poder de processamento (sua aplicação [auth] atualiza então os hashes guardados durante os logins); hashes mais antigos continuam verificáveis, pois incluem seu número de iterações. E usa salt: um salt gerado aleatoriamente é misturado à senha antes do hash e guardado no próprio hash; assim, dois usuários com a mesma senha terão hashes diferentes. O [Django] também pode usar [Argon2] e [bcrypt] (configurando [PASSWORD_HASHERS]); o estudo de caso, cujo banco de dados contém hashes [bcrypt], usa diretamente a biblioteca [bcrypt];
    • linhas 33–38: o usuário de um login, ou [None]. [not in] verifica a ausência de uma chave; a atribuição [name, role, password_hash = ...] desempacota uma tupla: cada variável recebe o elemento correspondente.

import time

import jwt
from django.conf import settings
from django.contrib.auth.hashers import check_password

from . import users
from .users import User

# o nome do cookie que carrega o token
COOKIE = "token"


# o usuário, ou None se o login for desconhecido ou a senha estiver errada.
# check_password calcula o hash da senha digitada com o salt e o algoritmo do hash
# armazenado e depois compara os dois resultados
def validate(login: str, password: str) -> User | None:
    if not login or not password:
        return None
    user = users.find(login)
    if user is None or not check_password(password, user.password_hash):
        return None
    return user


# o token JWT do usuário, assinado com a chave secreta (HMAC-SHA256)
def create_token(user: User) -> str:
    now = int(time.time())
    # o conteúdo do token: os "claims" (declarações sobre o usuário)
    claims = {
        "sub": user.login,
        "name": user.name,
        "role": user.role,
        "iat": now,
        "exp": now + settings.JWT_DURATION_MINUTES * 60,
    }
    return jwt.encode(claims, settings.JWT_SECRET, algorithm="HS256")


# o usuário descrito por um token cuja assinatura e data de expiração são
# válidas; None caso contrário (token forjado, expirado ou ilegível)
def verify(token: str) -> User | None:
    try:
        # decode verifica a assinatura E a data de expiração (claim exp)
        claims = jwt.decode(token, settings.JWT_SECRET, algorithms=["HS256"])
    except jwt.InvalidTokenError:
        return None
    return User(claims["sub"], claims["name"], claims["role"], claims=claims)
    • Linha 5: a biblioteca [PyJWT];
    • linha 7: a função [check_password] do [Django];
    • linha 13: o nome do cookie que transporta o token;
    • linhas 19–25: verificação de um nome de usuário e de uma senha. [check_password] lê o algoritmo, o número de iterações e o salt do hash guardado, calcula o hash da senha digitada com eles e compara os dois resultados (em tempo constante, veja o exemplo 23). Um nome de usuário desconhecido e uma senha incorreta produzem o mesmo resultado, [None];
    • linhas 29–39: geração do token. Seu conteúdo é um dicionário de claims sobre o usuário. Alguns têm nomes padronizados: [sub] (subject), o identificador do usuário; [iat] (issued at), a data de criação; [exp] (expiration), a data de expiração. As datas são expressas em segundos decorridos desde 1º de janeiro de 1970 ([time.time()] retorna esse número, incluindo as casas decimais, que [int] omite). Os demais campos são opcionais: aqui, o nome e o papel. [jwt.encode] gera o token e o assina com o algoritmo [HS256] (HMAC-SHA256, uma assinatura com chave secreta compartilhada);
    • linhas 44–50: verificação do token. [jwt.decode] verifica a assinatura e a data de expiração e depois retorna as asserções. Qualquer anomalia (token forjado, expirado ou malformado) lança uma exceção da classe [jwt.InvalidTokenError] ou de uma de suas subclasses, que o bloco [except] intercepta. O parâmetro [algorithms] especifica a lista de algoritmos aceitos: um token que declare um algoritmo diferente (ou nenhum, [none]) seria rejeitado. O token válido se torna um [User], sem hash, junto com suas claims (parâmetro chamado [claims]).

    # security/middleware.py: AUTENTICAÇÃO: a cada requisição, quem é o usuário?

from django.shortcuts import redirect

from . import auth


class Authentication:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        # por padrão, o visitante é anônimo
        request.user = None
        token = request.COOKIES.get(auth.COOKIE)
        if token is not None:
            user = auth.verify(token)
            if user is None:
                # um token inválido (expirado, forjado): direto para /login, e nós
                # excluímos o cookie
                response = redirect("login")
                response.delete_cookie(auth.COOKIE)
                return response
            request.user = user
        return self.get_response(request)

    A cada requisição, antes da view:

    • linha 14: por padrão, o visitante é anônimo: [request.user] é igual a [None];
    • linhas 15–17: se a requisição contém o cookie do token, o token é verificado;
    • linhas 18–23: um token inválido (expirado ou forjado): o middleware responde por conta própria, sem invocar o restante do processamento, redirecionando para a página de login, e aproveita para apagar o cookie: [delete_cookie] adiciona à resposta um cookie vazio e já expirado;
    • linha 24: um token válido: o usuário que ele identifica é incluído na requisição. O usuário não é procurado na lista de usuários: o token basta, pois é assinado.

    O middleware não nega o acesso: ele determina quem é o usuário, ou determina que o usuário é anônimo. Isso é autenticação. As negações ficam a cargo do controle de acesso.

    # security/decorators.py: o controle de acesso das views

from functools import wraps

from django.shortcuts import redirect


# @login_required: a view só é executada para um usuário autenticado; um
# visitante anônimo é redirecionado à página de login
def login_required(view):
    @wraps(view)
    def wrapper(request, *args, **kwargs):
        if request.user is None:
            return redirect("login")
        return view(request, *args, **kwargs)
    return wrapper

    O decorador [@login_required] envolve uma view (Exemplo 08): se o usuário é anônimo, ele responde redirecionando para a página de login sem chamar a view; caso contrário, chama a view. [django.contrib.auth] fornece um decorador com o mesmo nome e a mesma função, [@login_required], que se baseia em seu próprio [request.user].

# autenticados

from django.conf import settings
from django.shortcuts import redirect, render
from django.views.decorators.http import require_GET, require_http_methods, require_POST

from security import auth
from security.decorators import login_required


@require_GET
def home(request):
    return redirect("profile")


# GET: o formulário; POST: o login (o token anti-CSRF foi verificado por
# CsrfViewMiddleware)
@require_http_methods(["GET", "POST"])
def login(request):
    if request.method == "GET":
        return render(request, "auth/login.html")
    login = request.POST.get("login", "")
    user = auth.validate(login, request.POST.get("password", ""))
    if user is None:
        # uma mensagem deliberadamente vaga: não dizemos se é o login ou a senha
        return render(request, "auth/login.html",
                      {"login": login, "error": "Incorrect login or password."})
    # o token, em um cookie: o JavaScript da página não consegue lê-lo
    # (httponly); ele não acompanha as requisições POST vindas de outros sites
    # (samesite); ele desaparece ao mesmo tempo que o token expira (max_age)
    response = redirect("profile")
    response.set_cookie(auth.COOKIE, auth.create_token(user),
                        max_age=settings.JWT_DURATION_MINUTES * 60, httponly=True, samesite="Lax")
    return response


# logout: somente por POST (um simples link, colocado em outro site, não pode
# desconectar o usuário sem que ele saiba); excluímos o cookie
@require_POST
def logout(request):
    response = redirect("login")
    response.delete_cookie(auth.COOKIE)
    return response


# request.user: o usuário autenticado, encontrado pelo middleware
@require_GET
@login_required
def profile(request):
    return render(request, "profile/profile.html", {"user": request.user})
    • linhas 19–22: o formulário de login, escrito à mão no template, é protegido contra requisições forjadas pelo middleware [CsrfViewMiddleware], como todos os formulários POST (Exemplo 18);
    • linhas 23–28: o processo de login. Se o login falha, o formulário é exibido novamente com o nome de usuário digitado e uma mensagem deliberadamente vaga: dizer “nome de usuário desconhecido” revelaria a um invasor quais nomes de usuário existem;
    • linhas 32–35: em caso de sucesso, o token é guardado em um cookie e o usuário é redirecionado para a página protegida (esquema PRG). from functools import wraps

from django.core.exceptions import PermissionDenied
from django.shortcuts import redirect


# @login_required: a view só é executada para um usuário autenticado; um
# visitante anônimo é redirecionado à página de login
def login_required(view):
    @wraps(view)
    def wrapper(request, *args, **kwargs):
        if request.user is None:
            return redirect("login")
        return view(request, *args, **kwargs)
    return wrapper


# @role_required("ADMIN"): um decorador PARAMETRIZADO (veja o exemplo 08). A view é
# executada somente se o usuário autenticado tiver o papel solicitado; caso contrário, a
# exceção PermissionDenied produz uma resposta 403 (veja security/errors.py)
def role_required(role):
    def decorator(view):
        @wraps(view)
        @login_required
        def wrapper(request, *args, **kwargs):
            if not request.user.has_role(role):
                raise PermissionDenied(f"role {role} required")
            return view(request, *args, **kwargs)
        return wrapper
    return decorator
    • linhas 23–32: um decorador parametrizado (exemplo 08), [@role_required("ADMIN")]. O wrapper é, por sua vez, envolvido por [@login_required]: um visitante anônimo é primeiro enviado à página de login; um usuário autenticado que não tem o papel exigido dispara a exceção [PermissionDenied] (exemplo 24), que resultará em um erro 403 (Forbidden).

    A diferença entre os dois cenários de negação é significativa: um visitante anônimo que solicita uma página protegida é redirecionado para a página de login; um usuário autenticado que não tem o papel exigido recebe um erro 403 — fazer login não adiantaria nada, pois ele já está autenticado.

# GET: o formulário; POST: o login (o token anti-CSRF foi verificado por
# CsrfViewMiddleware)
@require_http_methods(["GET", "POST"])
def login(request):
    if request.method == "GET":
        return render(request, "auth/login.html")
    login = request.POST.get("login", "")
    user = auth.validate(login, request.POST.get("password", ""))
    if user is None:
        # uma mensagem deliberadamente vaga: não dizemos se é o login ou a senha
        return render(request, "auth/login.html",
                      {"login": login, "error": "Incorrect login or password."})

    # (httponly); ele não acompanha as requisições POST vindas de outros sites
    # (samesite); ele desaparece ao mesmo tempo que o token expira (max_age)
    response = redirect("profile")
    response.set_cookie(auth.COOKIE, auth.create_token(user),
                        max_age=settings.JWT_DURATION_MINUTES * 60, httponly=True, samesite="Lax")
    return response

# desconectar o usuário sem que ele saiba); excluímos o cookie
@require_POST
def logout(request):
    response = redirect("login")
    response.delete_cookie(auth.COOKIE)
    return response

def svg(text: str) -> str:
    w, h = WIDTH, HEIGHT
    parts = [f'<svg xmlns="http://www.w3.org/2000/svg" width="{w}" height="{h}" viewBox="0 0 {w} {h}">',
             '<rect width="100%" height="100%" fill="#f5f7fa"/>']
    # os caracteres: cada um ampliado, inclinado, deslocado, e cada ponto levemente
    # movido ao acaso
    step = (w - 20) / len(text)
    for i, character in enumerate(text):
        scale = random(4.6, 5.6)    # tamanho de uma unidade da grade, em pixels
        angle = random(-0.35, 0.35)   # rotação, em radianos (cerca de ±20°)
        cx = 10 + step * (i + 0.5) + random(-3, 3)    # centro do caractere
        cy = h / 2 + random(-4, 4)
        for stroke in FONT[character]:
            d = []
            # range(0, n, 2): 0, 2, 4... um ponto = dois números
            for k in range(0, len(stroke), 2):
                # ponto da grade, centralizado em (2, 3), distorcido, girado, posicionado
                x = (stroke[k] - 2 + random(-0.2, 0.2)) * scale
                y = (stroke[k + 1] - 3 + random(-0.2, 0.2)) * scale
                px = cx + x * math.cos(angle) - y * math.sin(angle)
                py = cy + x * math.sin(angle) + y * math.cos(angle)
                d.append(f"{'M' if k == 0 else 'L'}{px:.1f} {py:.1f}")
            parts.append(f'<path d="{" ".join(d)}" fill="none" stroke="{color()}" '
                         f'stroke-width="{random(2.2, 3):.1f}" stroke-linecap="round" '
                         f'stroke-linejoin="round"/>')
    # 3 traços de embaralhamento: curvas que cruzam a imagem
    for _ in range(3):
        parts.append(f'<path d="M{random(0, 20):.1f} {random(5, 45):.1f} '
                     f'C{random(30, 60):.1f} {random(0, 50):.1f} {random(90, 120):.1f} '
                     f'{random(0, 50):.1f} {random(130, 150):.1f} {random(5, 45):.1f}" '
                     f'fill="none" stroke="{color()}" stroke-width="1.3"/>')
    parts.append("</svg>")
    return "".join(parts)

    id: str
    svg: str


def generate() -> Captcha:
    text = captcha_drawing.random_text(5)
    # um identificador aleatório, impossível de adivinhar: 12 bytes sorteados por um
    # gerador criptográfico, escritos em hexadecimal

# o captcha é CONSUMIDO em todos os casos: uma imagem só é usada uma vez
def verify(id: str, entered: str) -> bool:
    if not id or not entered:
        return False
    # get retorna o valor, ou None; delete remove a resposta do cache, seja ela
    # certa ou não
    expected = cache.get(f"captcha.{id}")
    cache.delete(f"captcha.{id}")
    if expected is None:
        return False    # identificador desconhecido, ou captcha expirado
    # casefold: a string em minúsculas, para uma comparação que ignora maiúsculas e minúsculas
    return expected.casefold() == entered.strip().casefold()

import time

from django.conf import settings
from django.core.cache import cache


# as falhas de um cliente são contadas em uma JANELA de tempo fixa: no máximo
# LOGIN_MAX_FAILURES falhas por janela de LOGIN_WINDOW_SECONDS segundos
class Limiter:
    def __init__(self, ip: str):
        self.key = f"login.{ip}"

    # os segundos a esperar se o cliente estiver bloqueado, 0 caso contrário
    def wait(self) -> int:
        state = cache.get(self.key)
        if state is None or state["failures"] < settings.LOGIN_MAX_FAILURES:
            return 0
        return max(1, int(state["end"] - time.time()))

    # uma falha a mais
    def failure(self) -> None:
        state = cache.get(self.key)
        if state is None:
            # uma nova janela começa
            state = {"failures": 0, "end": time.time() + settings.LOGIN_WINDOW_SECONDS}
        state["failures"] += 1
        # a chave desaparece do cache no final da janela (timeout, em segundos)
        cache.set(self.key, state, timeout=max(1, int(state["end"] - time.time())))

    # um login bem-sucedido zera as falhas
    def clear(self) -> None:
        cache.delete(self.key)

    O limitador conta as tentativas malsucedidas de um cliente dentro de uma janela de tempo fixa: no máximo três tentativas malsucedidas por janela de 60 segundos, contados a partir da primeira tentativa malsucedida. Cada cliente é identificado por seu endereço IP.

    • linha 13: a chave de cache, específica do cliente: [login.127.0.0.1];
    • linhas 16–20: o número de segundos a esperar se o cliente está bloqueado (o número de falhas atingiu o máximo), 0 caso contrário. O estado guardado no cache é um dicionário: o número de falhas e o instante de término da janela;
    • linhas 23–30: mais uma falha. Se não há estado no cache, uma nova janela começa. O estado é reescrito com uma duração que expira no fim da janela: o cache o esquecerá então automaticamente, e o cliente recomeçará do zero;
    • linhas 33–34: uma conexão bem-sucedida apaga as falhas.

    Este limitador, escrito para fins ilustrativos, tem uma fraqueza: duas falhas simultâneas poderiam ler o mesmo estado e contá-lo como apenas uma. O cache do [Django] oferece operações atômicas ([cache.add], que só grava se a chave não existe, e [cache.incr], que incrementa um número), que são usadas na versão do estudo de caso. Também há bibliotecas prontas ([django-ratelimit], [django-axes]).

def home(request):

# GET: o formulário; POST: o login, com captcha e limitação das tentativas
@require_http_methods(["GET", "POST"])
def login(request):
    if request.method == "GET":
        return login_page(request)
    login = request.POST.get("login", "")
    # o limitador DESTE cliente: suas falhas são contadas sob seu endereço IP
    limiter = Limiter(request.META["REMOTE_ADDR"])
    # 1. um endereço bloqueado nem sequer é ouvido
    seconds = limiter.wait()
    if seconds > 0:
        return login_page(request, login, f"Too many attempts: try again in {seconds} s.")
    # 2. primeiro o captcha (barato), depois a senha (PBKDF2, caro)
    if not captchas.verify(request.POST.get("captcha_id", ""), request.POST.get("captcha", "")):
        limiter.failure()
        return login_page(request, login, "The code of the image is incorrect.")
    user = auth.validate(login, request.POST.get("password", ""))
    if user is None:
        limiter.failure()
        return login_page(request, login, "Incorrect login or password.")
    limiter.clear()
    response = redirect("profile")
    response.set_cookie(auth.COOKIE, auth.create_token(user),
                        max_age=settings.JWT_DURATION_MINUTES * 60, httponly=True, samesite="Lax")
    return response


# cada exibição do formulário constrói um NOVO captcha
def login_page(request, login="", error=None):
    return render(request, "auth/login.html",
                  {"login": login, "error": error, "captcha": captchas.generate()})

# desconectar o usuário sem que ele saiba); excluímos o cookie

def logout(request):

    response.delete_cookie(auth.COOKIE)

@require_GET
